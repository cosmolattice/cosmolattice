# CosmoLattice parameter database schema

This document describes the structure of `parameters.yaml`, the single source of
truth for every CosmoLattice input parameter (the framework parameters plus the
parameters of every shipped model). The file is generated by automated extraction
from the source headers; descriptions are intended to be curated over time.

## Top-level structure

```yaml
metadata:
  schema_version: 1
  description: "..."
  field_order: [name, type, enum_values, arity, required, default, important, scope, category, units, description, constraints]
parameters:
  - name: ...
    type: ...
    # ... (the 11 fields below)
```

- **`metadata`** — bookkeeping for the database.
  - `schema_version` — integer version of this schema (currently `1`).
  - `description` — human-readable summary of the file.
  - `field_order` — the canonical ordering of the 11 per-parameter fields; every
    entry under `parameters` emits its keys in this exact order.
- **`parameters`** — a flat list of parameter entries. Entries are grouped for
  readability with a `# === <scope> / <category> ===` comment before each group:
  framework entries come first (ordered by category: `run`, `IC`, `output`,
  `spectra`, `snapshots`, `GW`, `saving`, `couplings`), followed by model entries
  grouped by `scope` with `model:lphi4` (the default model) first and the rest in
  alphabetical order. Original ordering is preserved within each group.

## Per-parameter fields

Each entry under `parameters` has exactly these 11 fields:

| Field | Meaning |
|-------|---------|
| `name` | The parameter name as it appears in the input/parameter file (string). |
| `type` | The value type. One of the **type value set** below. |
| `enum_values` | For `type: enum`, a flow array of the allowed string values; otherwise `null`. |
| `arity` | Number of values the parameter takes: a literal count (e.g. `"1"`, `"2"`) or a symbolic count (see **symbolic-arity convention**). |
| `required` | Boolean; `true` if the parameter must be supplied, `false` if it has a default / is optional. |
| `default` | The default value used when the parameter is omitted. A literal value, a symbolic/computed string (see **symbolic-default convention**), or `null` when there is no default. Always stored as a string or `null`. |
| `important` | Boolean; `true` flags parameters that are commonly tuned / particularly significant for a run. |
| `scope` | Where the parameter lives: `framework`, or `model:<modelName>` for a model-specific parameter. |
| `category` | Functional grouping of the parameter. One of the **category value set** below. |
| `units` | Physical/program units of the value. One of the **units value set** below. |
| `description` | Human-readable description of the parameter's meaning. |
| `constraints` | Free-text notes on constraints, mutual exclusivity, valid ranges, or `null`. |

## Allowed value sets

### `type` value set
- `int` — integer scalar(s).
- `float` — floating-point scalar(s).
- `bool` — boolean flag (`true`/`false`).
- `string` — free-form string (e.g. a path or label).
- `enum` — restricted to one of a fixed set of strings listed in `enum_values`.

### `category` value set
Framework categories (in their canonical emission order):
- `run` — core run / lattice / time-evolution parameters.
- `IC` — initial-condition controls.
- `output` — measurement and output controls.
- `spectra` — power-spectrum / binning controls.
- `snapshots` — field-snapshot output controls.
- `GW` — gravitational-wave measurement controls.
- `saving` — checkpoint / save-and-restore controls.
- `couplings` — framework-level coupling parameters.

Model category:
- `model` — model-specific parameter (used for all `model:*` scopes).

### `units` value set
- `dimensionless` — pure number.
- `program units` — CosmoLattice internal/program units.
- `GeV` — energy units.
- `GeV^2` — energy-squared (e.g. mass-squared) units.
- `path` — a filesystem path.
- `n/a` — not applicable (e.g. boolean flags or pure labels).

## Symbolic-arity convention

When a parameter's arity is not a fixed literal but depends on the model/run
configuration, `arity` stores a symbolic token verbatim:

- `NS` — number of scalar fields.
- `#U1` — number of U(1) gauge sectors.
- `#couples` — number of coupled pairs/couplings.
- `#SU2` — number of SU(2) gauge sectors.
- `#NMC` — number of non-minimally-coupled fields.
- `NDim` — number of spatial lattice dimensions (1, 2 or 3). One value is
  supplied per dimension.

These may also appear in simple arithmetic (e.g. `NS`, `#U1`) and are stored as
strings so they can be resolved at parse time against the concrete configuration.

### A note on `NDim` and the snapshot sub-volume parameters

The snapshot sub-volume parameters (`snap_lowercoord`, `snap_uppercoord`,
`snap_stepcoord`) use `arity: NDim`: you supply **one value per spatial
dimension** — three numbers for a 3D run, two for 2D, one for 1D.

These previously read `arity: 10`, which was misleading. The `10` is *not* a
required field count: it is the fixed capacity of the internal array the HDF5
saver pre-allocates (the maximum `NDim` the I/O layer supports). At parse time
the saver keeps only the first `NDim` entries (`for i < NDim`) and discards the
rest. Concretely:

- Supply exactly `NDim` values (e.g. `snap_lowercoord = 0 0 0` for 3D).
- Supplying more than `NDim` values up to 10 is harmless — entries beyond `NDim`
  are ignored.
- Supplying fewer values pads the remainder with the default for that parameter.

So you never need to type 10 numbers; the meaningful length is always `NDim`.

The related `energy_snapshot` parameter keeps `arity: 14`, but the same caveat
applies: the `14` is a **maximum**, not a required count. It is the number of
distinct recognised snapshot labels (`S`, `E_S_K`, `E_S_G`, `CS`, `E_CS_K`,
`E_CS_G`, `E_SU2D_K`, `E_SU2D_G`, `E_A_K`, `E_A_G`, `E_B_K`, `E_B_G`, `E_V`,
`E`). You supply a **space-separated subset** of those labels — list only the
quantities you want saved, in any order. The parser checks membership of each
recognised label in your list and caps it at 14; omitting the parameter (or
giving an empty list) saves no snapshots. It is left as `type: string` with
`arity: 14` rather than `type: enum` because it is a multi-value subset, not a
single choice from a fixed set.

## Symbolic-default convention

Defaults that are computed from other parameters (rather than literal constants)
are stored verbatim as strings, e.g.:

- `"10*dt"` — ten times the time step.
- `"2*kUV"` — twice the ultraviolet cutoff.
- `"{0,0}"` — a literal compound/zero-initialized value.

The consumer is responsible for evaluating these expressions in the context of a
specific run. A `default` of `null` means there is no default value.

## The three enum value sets

Exactly three parameters use `type: enum`, each with its own value set:

1. **`ICtype_S`** — scalar-sector initial-condition type:
   `["Default", "RandomWithMatter", "DefectsNetwork", "DefectsWhiteNoise", "Homogeneous"]`.
2. **`ICtype_U1`** — U(1)-sector initial-condition type:
   `["Default", "RandomWithMatter", "PlaneWaves", "PlaneWavesZeroB", "BunchDavisTransverseU1", "DefectsNetwork", "DefectsWhiteNoise"]`.
3. **`evolver`** — time-evolution integrator:
   `["LF", "VV2", "VV4", "VV6", "VV8", "VV10", "VV6_2", "RK2", "RK3_3", "RK3_4", "RK4_5", "PV2", "PV4", "PV6", "PV8", "PV10", "PV6_2"]`.
